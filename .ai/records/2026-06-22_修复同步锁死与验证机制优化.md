# 2026-06-22 修复同步锁死与验证机制优化

## 背景 & 问题描述
用户反馈移动端更新了数据，但网页端到目前为止依然没有同步更新，且在网页端的同步面板中，“上传到云端”与“从云端下载”两个按钮显示为置灰状态，完全无法使用。

## 🔍 问题排查与定位
经过对代码的审查，定位到以下两个相互关联的核心原因：
1. **GitHub 网络连接挂起（导致按钮彻底灰显卡死）**：
   - 网页端的同步状态由 React 的 `isSyncing` 控制。
   - 在国内网络环境下，GitHub Gist API (`api.github.com`) 极易被墙或发生连接拥堵。由于之前代码中的 `fetch` 均未配置超时，一旦网络连接遭遇挂起，`fetch` 状态将处于无限 Pending 状态。
   - 这会导致 `handleDownload` 或 `handleUpload` 中的 `finally` 块（负责执行 `setIsSyncing(false)`）无法被执行，从而让 `isSyncing` 永久卡在 `true`，同步按钮彻底置灰锁定。

2. **强验证逻辑导致 Token 无法存入**：
   - 之前在 `SyncModal.tsx` 中配置 Token 时，只有当向 GitHub 发起的 `verifyToken` 请求验证成功（返回 `true`）才会调用 `onSaveConfig` 写入 LocalStorage。
   - 如果用户当前所在的网络环境（例如电脑网页端）访问 `api.github.com` 被挂起或返回失败，则 `verifyToken` 强制判定为无效，这导致合法的 Token 根本无法被保存，从而按钮因为 `!config.githubToken` 判定为真而始终置灰。

## 🛠 解决方案与修改内容
1. **网络请求增加超时防护 (`services/githubGistService.ts`)**：
   - 引入带有 `AbortController` 的 `fetchWithTimeout` 辅助方法，并将所有向 GitHub API 的请求超时时间统一限制为 **8秒**（上传/下载较大数据限制为 **10秒**）。
   - 即使网络被墙或拥堵，请求也会在 8 秒内自动熔断并抛出异常，触发 `finally` 块重置 `isSyncing = false`，防止按钮被永久锁死。

2. **重构 `verifyToken` 返回值类型**：
   - 将其返回值从单纯的 `boolean` 重构为 `{ isValid: boolean; errorType?: 'network' | 'unauthorized' }`。
   - 区分“Token 本身无效（401/403）”与“网络连接失败（捕获异常）”两种情况。

3. **允许网络受阻时强制保存 (`components/SyncModal.tsx`)**：
   - 在 `handleVerify` 中，如果验证不通过且是因为 `network` 原因，向用户弹出二次确认提示：“是否强制保存 Token”。
   - 若用户确认，则保存 Token 并提醒其确保后续网络通畅，实现了容灾保存，进而让按钮亮起可点。

## 验证结果
- 无论网络是否成功，同步按钮均可在超时（最大 8s/10s）后正常重置，不再发生置灰卡死。
- 当处于代理未走或网络被墙环境时，可弹窗确认强制保存 Token，解锁同步按钮。
